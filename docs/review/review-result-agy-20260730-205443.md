### 종합 평가
- 전체 점수: 8.5/10
- 한줄 요약: Fabric.js 7 도입에 따른 API 변경 리스크를 파악하고 현실적인 MVP 범위를 설정한 우수한 설계 문서이나, 키보드 단축키 충돌, 비동기 상태 복구, 모바일 터치 이벤트 오작동 등 캔버스 웹 앱 고유의 엣지 케이스 처리에 대한 보완이 필요합니다.

### 구체적 피드백

1. **[Blocker] 글로벌 단축키와 입력 필드(텍스트 편집) 간 충돌 제어 누락**
   - 캔버스 내 텍스트 인라인 편집 모드(`Text.isEditing`)나 우측 속성 패널의 입력 창(숫자/텍스트 입력 필드)에 포커스가 가 있을 때, `Delete`, `Backspace`, `Ctrl+Z`, `Ctrl+D` 등의 단축키가 전역적으로 작동하여 편집 중인 객체가 삭제되거나 캔버스 상태가 복구되는 치명적인 버그가 발생할 수 있습니다. 
   - **해결 방안**: 단축키 이벤트 리스너에서 `document.activeElement`가 `input`, `textarea`이거나 Fabric 텍스트 객체가 인라인 편집 중인 상태인 경우 이벤트를 무시(Ignore)하는 로직을 추가해야 합니다.

2. **[Blocker] Fabric 7 `loadFromJSON` 비동기 처리에 따른 Race Condition**
   - Fabric 7에서 `loadFromJSON`은 Promise를 반환하는 비동기 함수로 변경되었습니다. 되돌리기(Undo/Redo) 단축키를 연타할 때, 이전 상태 복구 프로세스가 끝나기 전에 다음 상태 복구가 호출되면 캔버스 렌더링 상태와 내부 데이터가 꼬이게 됩니다.
   - **해결 방안**: 상태 복구 중인지 여부를 추적하는 Flag(예: `isRestoringState`)를 두어 복구 작업 진행 중에는 단축키 입력을 잠금(Lock) 처리하거나 큐에 적재해야 합니다.

3. **웹폰트 로드 대기 및 로딩 중 객체 상태 변경 예외 처리**
   - `document.fonts.load`를 통해 5초간 대기하는 동안 사용자가 해당 텍스트 객체를 삭제하거나 페이지를 이탈할 수 있습니다. 로드 완료 콜백 시점에 이미 존재하지 않는 객체의 `initDimensions()`를 호출하려고 시도할 때 발생할 수 있는 Null Pointer 에러에 대비해야 합니다.
   - 폰트 로드 완료 후 캔버스 화면을 다시 그리기 위한 `canvas.requestRenderAll()` 호출도 누락 없이 반영되어야 시각적 깨짐을 방지할 수 있습니다.

4. **모바일 캔버스 영역 터치 동작과 브라우저 기본 스크롤 충돌**
   - 모바일(900px 미만) 화면에서 사용자가 캔버스 위 객체를 손가락으로 드래그하여 이동할 때, 모바일 브라우저의 기본 페이지 스크롤(Scroll & Bounce) 및 핀치 줌이 동시에 트리거되어 오작동을 일으킬 수 있습니다.
   - **해결 방안**: 캔버스 엘리먼트 및 부모 컨테이너에 `touch-action: none` CSS 스타일을 지정하여 기본 스크롤을 방지하고 터치 이벤트를 캔버스 내부 조작으로 한정해야 합니다.

### 개선 제안

1. **(우선순위: 상) Local Storage 기반 임시 자동 저장(Autosave) 도입**
   - 2차 범위로 "저장/불러오기"를 제외하여 사용자 이탈 경고창만 제공하고 있으나, 브라우저가 예기치 않게 종료되거나 실수로 새로고침을 누르는 경우 작업 내역이 유실되어 사용자 경험이 악화될 수 있습니다.
   - DB 서버가 필요 없는 가벼운 **Local Storage Autosave** 훅을 구현하여, 캔버스 스냅샷이 기록될 때마다 Local Storage에 직렬화된 JSON을 저장하고 재진입 시 복구할 것인지 묻는 모달을 띄워주는 방안을 제안합니다.

2. **(우선순위: 중) 캔버스 프리셋 변경 시 비례 재배치 방식 정의**
   - 가로세로 비율 차이가 큰 화면(예: 16:9에서 1:1)으로 변경 시, 객체들을 캔버스 중심점을 기준으로 스케일링할 것인지 혹은 좌상단(0,0)을 기준으로 이동시킬 것인지 수학적 변환 공식이 사전에 구체화되어야 개발 단계의 지연을 막을 수 있습니다. 객체의 중심점(Center)을 유지한 채 스케일 변화율을 적용하는 방식을 권장합니다.

3. **(우선순위: 하) 모바일 픽셀 상한선 및 내보내기 배율 제한 다변화**
   - 모바일 사파리 등 일부 모바일 브라우저 환경에서는 메모리 제한으로 인해 큰 해상도(예: 1600만 픽셀 부근)의 Canvas를 이미지로 변환(`toDataURL`)할 때 브라우저 탭이 다운되는 크래시 현상이 자주 보고됩니다. 데스크톱의 1600만 픽셀 제한보다 모바일은 한 단계를 더 낮춘 안전 수준(예: 최대 400만 픽셀 이하)으로 상한선을 이원화하여 지정할 필요가 있습니다.
