### 종합 평가
- **전체 점수**: 7.5/10
- **한줄 요약**: 기존 감사 파이프라인의 안전장치를 영리하게 활용한 실용적인 설계이나, **재크롤 실패에 따른 부분 적용 위험, run 중단 시의 멱등성(고아 데이터), 그리고 특정 예외 건(`nullify`)에 대한 사후 처리 구체성**이 보완되어야 합니다.

### 구체적 피드백

#### 1. [Blocker] 재크롤 실패 시 부분 적용 위험 및 대응책 부재 (3.9, 2절 관련)
- **현 설계의 문제**: 3.9절에서 재크롤 실패 시 "해당 건 finding 미적재 후 나머지는 계속 진행"하도록 되어 있습니다. 그러나 2절에서 "승인 패키지 1회 일괄 승인"을 결정했으므로, 실패 건이 섞인 상태로 진행하면 일부 폰트가 누락된 불완전한 패키지가 그대로 배포됩니다.
- **해결 방안**: 크롤 실패율이 높지 않을 것이므로(185종), 재크롤 단계에서 오류 발생 시 전체 프로세스를 즉시 중단(Abort)하거나, 실패한 건들만 골라 재시도(Retry)할 수 있는 CLI 옵션을 설계에 추가해야 합니다.

#### 2. [Blocker] 감사 run 중단/재실행 시 고아 데이터 누적 및 중복 finding 위험 (3.9, 3.3절 관련)
- **현 설계의 문제**: run 중단 시 완료되지 않은 run이 DB에 그대로 남고, 재실행 시 새 run을 생성합니다. 이때 이전 실행에서 이미 적재된 snapshot과 finding들이 DB에 고스란히 남아 중복 데이터가 되거나, DB 고유 제약조건(Unique Constraint)에 걸려 재실행 자체가 실패할 위험이 있습니다.
- **해결 방안**: 실행 흐름 시작 시, 완료되지 않은 기존 run이 있다면 이를 먼저 `Failed` 또는 `Aborted` 상태로 마킹하고 관련 finding을 정리(cleanup)하는 단계를 추가하거나, `run` 생성 시 동일 대상에 대해 멱등성(Idempotency)을 보장하는 적재 메커니즘을 정의해야 합니다.

#### 3. [Minor] dev/prod 적용 시간차로 인한 낙관적 잠금 충돌 시 복구 시나리오 미비 (3.7, 3.8절 관련)
- **현 설계의 문제**: dev 적용 검증 후 prod 적용 사이에 시간차가 발생해 prod의 특정 폰트가 수정되면, `expected_updated_at` 불일치로 `preflight`나 `apply`가 거부됩니다. 이는 안전장치로서 잘 작동하는 것이나, 이 경우 manifest를 재빌드하고 다시 승인 프로세스를 밟아야 하는지 등 운영 관점의 복구 가이드가 명시되어 있지 않습니다.
- **해결 방안**: 충돌 발생 시 manifest를 prod 기준으로 즉시 갱신하여 덮어쓰는 복구 명령어 예시(`manifest build --target prod --force` 등)를 운영 단계에 추가하십시오.

#### 4. [Minor] `google-sans-flex` (`nullify` 1건)의 구체적인 최종 처리 방안 부재 (3.6절 관련)
- **현 설계의 문제**: `fonts.official_url`이 `NOT NULL` 제약조건이 있어 비울 수 없기 때문에, `nullify` 판정 건은 `auto_applicable=False`로 두고 근거만 남긴다고 했습니다. 하지만 이 상태로 두면 해당 폰트의 오염된 URL은 계속 프로덕션에 남아 있게 됩니다.
- **해결 방안**: 이 1건에 대해 임시로 대체할 안전한 default URL(예: Google Fonts 공식 주소)을 수동 승인(`manual_review`와 동일 처리) 단계에서 기입하여 정정할 것인지, 아니면 공백 문자나 특정 플레이스홀더를 넣을 것인지 구체적인 도달 목표를 결정해야 합니다.

#### 5. [Minor] 판정 불일치 건의 자동 승인(auto-approve) 배제 필터링 누락 (3.3, 3.9절 관련)
- **현 설계의 문제**: 3.3절의 5단계에서 대조 보고(07-29 판정 vs 현재 판정)를 수행하고 불일치 시 새 값을 사용한다고 명시했습니다. 그러나 만약 `auto_fix_safe`로 분류되었던 건이 재크롤 시점에 판정이 바뀌어 `manual_review`나 `nullify` 수준으로 강등되어야 하는 경우, 이 건이 자동으로 `auto-approve` 대상에서 제외되는지에 대한 필터링 논리가 명확하지 않습니다.
- **해결 방안**: 실시간 판정이 완료된 후, `auto_applicable` 플래그를 실시간 판정 결과 기준으로 재평가하여 적재하도록 확실히 명시해야 합니다.

#### 6. [Info] 단일 evidence 공유 구조의 타당성 및 DB 제약 조건 검증 (3.5절 관련)
- **검토 의견**: `official_url`과 `license_source_url` 두 finding이 단일 `evidence_id`(동일 HTML snapshot)를 공유하는 것은 논리적으로 매우 타당합니다. 단, 기존 감사 프레임워크의 DB 스키마가 `finding.evidence_id`에 대해 Unique 제약 조건을 가지고 있지 않은지 사전에 확인이 필요합니다.

#### 7. [Info] 수동 위주의 완료 기준 보완 (5절 관련)
- **검토 의견**: 완료 기준 4번("재배포 후 폰트 상세 화면에서 직접 확인")은 174종 전체를 검증하기에 비효율적입니다. 완료 기준 검증을 위해 "DB에서 `official_url`에 눈누 SNS 도메인이 남아있는지 확인하는 SQL 쿼리 결과 0건"과 같은 객관적이고 자동화된 검증식을 완료 기준에 명시하는 것을 권장합니다.

### 개선 제안

1. **[우선순위 상] 멱등성 확보를 위한 Run Cleanup 명령어 지원**
   - 감사 파이프라인의 안정성을 위해, 불완전하게 종료된 run을 삭제하거나 롤백할 수 있는 `font-audit clean --run-id <ID>` 형태의 툴링을 지원하여 고아 run 문제를 해결할 것을 제안합니다.
2. **[우선순위 중] 1단계 진입 전 prod DB `font_sources` 사전 검증(Dry-run) 자동화**
   - 3.7절의 `⚠️ 미검증` 사항인 prod DB 내 185종 `provider_record_id` 누락 여부 조회를 단순 수동 조회가 아닌, `scan` 혹은 `preflight` 명령어 실행 시 첫 단계에서 자동으로 assert하는 코드로 녹여내어 인적 실수를 방지할 것을 제안합니다.
3. **[우선순위 하] 검증 쿼리 셋 작성**
   - 완료 검증 단계에서 실행해 볼 수 있는 SQL 템플릿(예: 정정 대상 174종 목록의 before/after 대조 쿼리)을 `docs` 또는 `scripts/` 내에 함께 커밋해두면 배포 후 최종 검수 시간을 크게 단축할 수 있습니다.
