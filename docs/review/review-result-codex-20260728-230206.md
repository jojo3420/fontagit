### 구체적 피드백

1. [Blocker] `mismatch`를 곧바로 정정 대상으로 보는 기준이 약합니다.  
   재추출 값이 DB와 다르다고 해서 새 값이 항상 정답은 아닙니다. 새 추출기도 “본문 첫 외부 링크”에 의존하므로 오탐 가능성이 있습니다.

2. [Blocker] `license_verified=false`로 내리는 기준이 더 명확해야 합니다.  
   `official_url`만 잘못된 것인지, `license_source_url`도 새로 확보되는지, 라이선스 본문 근거가 있는지에 따라 처리 기준이 달라집니다.

3. prod 적용 승인 전에 보여줄 “쿼리 전문”만으로는 부족합니다.  
   최소한 변경 전/후 건수, 샘플, 되돌리기 manifest, 영향받는 slug 목록, `license_verified` 변경 수를 같이 보여줘야 합니다.

4. `no_link`, `no_container` 처리 방침을 뒤로 미루는 것은 맞지만, 리포트 형식에는 반드시 포함되어야 합니다.  
   예: `recommended_action: update | keep | nullify | manual_review`.

5. `official_url`을 manifest 허용 필드에 추가하는 설계는 타당합니다.  
   다만 `official_url`이 낙관적 잠금 기준이자 변경 대상이면 동시 실행 충돌 테스트가 필요합니다.

6. #141의 브라우저 User-Agent 적용은 민감합니다.  
   “사용자 승인”만 쓰지 말고, 어떤 UA를 쓸지, robots.txt를 어떻게 확인할지, 차단 시 어떻게 중단할지까지 적어야 합니다.

7. 본문 sanity 게이트는 좋은 보완입니다.  
   다만 “오류 페이지” 판정 기준이 없습니다. 제목, 본문 길이, 금칙어, expected domain, content-type 같은 최소 기준이 필요합니다.

8. 체크포인트 설계는 좋습니다.  
   `failed_font_ids`를 구조화하는 방향이 맞고, 문자열 파싱을 피한 것도 맞습니다.

9. 스캐너 중단/재개가 리스크에만 있고 설계에는 약합니다.  
   진행 상태 파일 위치, 저장 주기, 재시작 시 중복 요청 방지 방식을 명시해야 합니다.

10. 테스트 범위는 약간 넓습니다.  
   핵심은 #150 스캐너 판정, manifest 변경 안전성, #142 재개 누락 방지입니다. #141은 결함별 최소 케이스만 두는 게 적당합니다.

### 개선 제안

1. 우선순위 1: `mismatch` 후속 판정을 추가하세요.  
   `auto_fix_safe`, `manual_review`, `no_safe_candidate`처럼 자동 정정 가능 여부를 나누는 게 안전합니다.

2. 우선순위 2: prod 적용 전 승인 패키지를 정의하세요.  
   변경 건수, 변경 필드별 건수, 샘플 10개, 전체 slug 목록, 역방향 manifest, 검증 쿼리를 한 묶음으로 보여주는 방식이 좋습니다.

3. 우선순위 3: `license_verified` 정책표를 추가하세요.  
   예: 새 `license_source_url`이 제작사 페이지면 유지, 근거가 없으면 false, 판단 애매하면 manual review.

4. 우선순위 4: 리포트 JSON 스키마를 문서에 넣으세요.  
   구현자가 헷갈리지 않게 `font_id`, `slug`, `db_official_url`, `new_official_url`, `classification`, `recommended_action` 정도는 고정해야 합니다.

5. 우선순위 5: #141은 #150과 섞이지 않게 별도 PR로 유지하세요.  
   #150은 데이터 정정, #141/#142는 audit 파이프라인 수정입니다. 같이 묶으면 리뷰와 롤백이 어려워집니다.
