### Critical 이슈 - Must-fix (머지 차단)

#### 1. 실패 복구를 위한 재실행이 자기 자신의 `sort_order`와 충돌합니다

- 파일: `apps/pipeline/src/fontagit_pipeline/collections_seed.py:107-129, 146-164, 229-235`
- 문제: 첫 실행에서 컬렉션만 생성되고 아이템 저장이 실패하면, 다음 실행은 복구 로직에 도달하기 전에 중단됩니다.
- 근거(diff 인용): 충돌을 `existing_orders & {10, 11, 12, 13}`으로 계산한 뒤 `if report["sort_order_conflicts"]: ... return 1`로 종료합니다. 이미 생성된 동일 slug의 순번도 충돌로 취급됩니다.
- 제안 수정: `sort_order → slug` 관계를 비교해 다른 slug가 같은 순번을 쓸 때만 충돌로 판단해야 합니다. 동일 slug는 기존 컬렉션과 아이템을 검증·보정하도록 변경하고, “아이템 저장 실패 후 재실행 성공” 테스트를 추가하세요.

#### 2. 시드 작업이 원자적이지 않고 불완전한 결과도 성공 처리합니다

- 파일: `apps/pipeline/src/fontagit_pipeline/collections_seed.py:158-188, 236-245`
- 문제: 컬렉션과 아이템을 별도 요청으로 저장합니다. 기존 아이템이 한 개라도 있으면 완성된 것으로 간주하며, 후보가 5개 미만인 컬렉션은 건너뛰고도 최종적으로 `0`을 반환합니다.
- 근거(diff 인용): `if current.json(): ... return True`, 컬렉션 POST 후 별도 아이템 POST, 후보 부족 시 `continue`입니다.
- 제안 수정: 쓰기 전에 4개 계획을 모두 검증하고 하나라도 기준 미달이면 아무것도 쓰지 않은 채 실패해야 합니다. 가장 안전한 방식은 Supabase DB 함수(RPC) 하나로 컬렉션과 아이템을 트랜잭션 처리하는 것입니다. 어렵다면 `draft 생성 → 아이템 저장·검증 → published 전환` 순서로 처리하고, 기대한 font_id·개수와 실제 데이터를 비교하세요.
