- 전체 점수: 7/10
- 한줄 요약: 방향과 기능 범위는 좋지만, 구현 계획·데이터 식별자·비동기 상태 처리 정의가 부족해 바로 개발에 들어가면 재작업 위험이 큽니다.

### 구체적 피드백
1. [Blocker] Plan 문서가 없습니다. 현재 문서는 Design에 가깝고, 슬라이스별 작업 순서·완료 기준·검증 명령·수동 확인 항목이 없습니다. 구현 착수 전 별도 구현 계획이 필요합니다.

2. [Blocker] 폰트 상세 CTA 정책이 불완전합니다. Tier B는 웹폰트 파일이 없어 대상 외인데, 상세 페이지에 “이 폰트로 만들어보기” 버튼을 두면 사용자는 해당 폰트가 적용된다고 기대합니다. Tier A/self-host만 노출할지, Tier B에서는 비활성화할지 정해야 합니다.

3. 폰트 식별자 체계를 하나로 정해야 합니다. URL은 `slug`, 계측은 `font_id`, 구현 설명은 `fontKey`, 렌더링은 `fontFamily`를 씁니다. 이대로면 사용 중 폰트 목록, GA4, 상세 이동, undo/redo 복원이 어긋날 수 있습니다.

4. 폰트 굵기 대체 규칙이 빠졌습니다. 제목 700, 부제 500, 본문 400을 기본값으로 쓰지만 모든 폰트가 해당 weight를 지원하지 않을 수 있습니다. 가장 가까운 weight로 대체하는 규칙이 필요합니다.

5. undo/redo와 비동기 폰트 로딩 충돌 처리가 부족합니다. 폰트 로딩이 끝나기 전에 객체를 삭제하거나 undo하면 늦게 끝난 요청이 잘못된 객체에 반영될 수 있습니다. 객체 ID와 요청 세대 토큰이 같이 필요합니다.

6. Fabric snapshot 직렬화 규칙이 없습니다. `font_id`, `slug`, 사용 폰트 정보, 객체 ID 같은 커스텀 속성이 JSON에 보존되는지 정의해야 합니다.

7. 모바일 범위가 애매합니다. “이동과 선택만 지원”이면 텍스트 내용 편집은 가능한지 불명확합니다. 모바일에서 텍스트 추가·내용 수정·폰트 적용·내보내기 중 무엇이 되는지 명확히 해야 합니다.

8. 정렬·간격 계산 기준이 부족합니다. 회전, stroke, scale이 있는 객체를 `left/top` 기준으로 맞출지, 실제 bounding box 기준으로 맞출지 정해야 합니다.

9. 페이지 이탈 경고 구현 리스크가 있습니다. 브라우저 이탈은 가능하지만 사이트 내부 이동 확인은 Next App Router에서 까다로울 수 있습니다. 링크 클릭 래핑 또는 전역 차단 방식 중 하나를 정해야 합니다.

10. 내보내기 전 폰트 로딩 보장이 더 명확해야 합니다. PNG 생성 직전 사용 중인 모든 폰트가 로드됐는지 확인하지 않으면 화면과 PNG 결과가 다를 수 있습니다.

### 개선 제안
1. P0: 구현 계획 문서를 추가하세요. 9~10개 슬라이스를 “작업 내용 → 완료 기준 → 검증 방법 → 수동 확인”으로 쪼개야 합니다.

2. P0: 폰트 데이터 모델을 먼저 고정하세요. 최소 필드는 `id`, `slug`, `displayName`, `fontFamily`, `cssUrl`, `availableWeights`, `sourceTier`, `detailUrl` 정도가 필요합니다.

3. P0: 미지원 폰트 정책을 정하세요. 추천은 Tier A/self-host만 “이 폰트로 만들어보기”를 노출하는 방식입니다.

4. P1: undo/redo, 폰트 로딩, snapshot 복원을 별도 순수 로직으로 먼저 설계하세요. 이 부분이 깨지면 편집기 전체 신뢰도가 무너집니다.

5. P1: 모바일 MVP를 더 줄이세요. 1차는 “선택, 이동, 폰트 적용, PNG 내보내기”까지만 명확히 하고, 정밀 편집은 데스크톱 전용으로 두는 편이 안전합니다.

6. P2: 계측 파라미터를 보강하세요. `canvas_size`, `font_count`, `object_count`를 추가하면 “실험 경험” 성공 기준을 더 잘 볼 수 있습니다.
